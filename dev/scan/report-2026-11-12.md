# 跨两边兼容扫描报告（2026-11-12）

计划和分类见 [docs/cross-host-scan.md](../../docs/cross-host-scan.md)。本报告只列事实和复现方法；每一类怎么兼容，等和所有者定了规则再改代码。

## 怎么扫的

- 环境：`dev/` 测试环境，复用模式，DSH 0.2.2-rc.2。假 WSL 的 profile 装着 ds-bot、dsh-pet、dsh-claude-style、dsh-runtime-tuning（打开了 `tuned` 预设）。
- 重跑：`dev/scan/run.sh`（只读：`dev/scan/run.sh read`），结果在 `~/dshwsl-desk/scan/`。
- 脚本：
  - `inventory.mjs`：从 38 个官方包的 `typert.remote-client.d.ts` 列出页面能调的 **223 个接口**，请求类型展开三层，按我们的路由规则标出每个接口会被送到哪边。
  - `probe.mjs`：57 个只读接口，每个问三次再比较：Windows 端（绕过路由）、WSL 端（经桥）、页面（经路由）。带会话 id 的接口，用 Windows 任务和 WSL 任务各问一次。
  - `dynamic.mjs`：把设置临时写成"只有一边有"或"哪边都没有"的值，两边各新建一个任务，看各自的结果。另建一个 WSL 任务的定时任务，再通过页面查看和删除。每个用例结束都会还原：设置按原值写回并同步到 WSL，新建的任务归档，定时任务在 WSL 端直接删除。跑完核对过，三个 profile 的 `cordis.patch.yml` 和备份逐字相同。
  - `summary.mjs`：汇总差异。比较 schema 前先把内部编号（uid、refs、sKey）归一化。
- 三方读取覆盖不到的部分：
  - 流式接口（`*/watch`、`*/follow`）只做了静态判断。
  - 只在发消息时才会出错的情况（模型、搜索服务）没有实际发消息。
  - 测试 profile 没开的功能（liveshare、forge、cua、speech、插件市场，两边都返回 404）没有测。
  - 测试环境里没有"只在 WSL 才有的权限预设、模型服务商、MCP 服务器"，这几项是根据代码推断的。

## 总体结论

1. **按会话分流的部分没有问题。**
   - 路由规则：清单里 110 个接口按调用里的会话或工作区 id 分流。
   - 只读接口：带 WSL 任务调用 18 次（其中 12 次两边都有正常结果，其余是两边返回同样的错误），18 次全部到了 WSL 端，页面拿到的和 WSL 端一致。
   - `session/create` 和 `agentPresets/select` 也按运行位置分流了。
2. **问题集中在两处。**
   - **设置里的值指向某一边才有的东西**：预设、权限预设、搜索服务、模型、MCP 命令、环境变量名。DSH 只存一个值，却是由各自的 Host 去解析。
   - **主机级接口**：调用里没有任何会话 id，于是永远只到 Windows 端。这样的接口有 44 个，另有 47 个所在的命名空间被我们刻意留在本机。
     - 其中大部分本来就该只看 Windows：账户、语音、屏幕操作、目录选择、插件管理有专门的 WSL 标签页。
     - 但有一批列的是"每个 Host 自己的东西"：定时任务、MCP 服务器状态、插件清单、搜索服务、权限预设、模型目录。页面上看不到 WSL 的那一份。

## 发现

严重程度：**高** = 功能坏了或静默失败；**中** = 看不到、选不了，或显示和实际不一致；**低** = 只影响显示或很少遇到。

### 第 1 类：跨边引用（设置值指向只在一边存在的东西）

| # | 设置 | 现象 | 验证 | 严重 |
|---|---|---|---|---|
| 1 | `agent-preset-registry.selectedDefault`（新任务默认预设） | 设成 WSL 独有的 `tuned`：WSL 任务正常；**Windows 任务建不出来**（`agent-preset/not-found: Unknown agent preset: tuned`）；预设页没有任何卡片显示「新任务默认」 | 动态，已复现 | 高 |
| 2 | `permission.defaultPreset`（默认权限预设） | 值不在本端清单里时，**两边建任务都会失败**（`gateway/internal: permission: unknown default preset`）。机制和第 1 条一样：只要 WSL 插件加了权限预设，设成默认后 Windows 任务就建不出来。另外权限预设清单（`permissionPresets/catalog`）只读 Windows，页面上选不到 WSL 的权限预设 | 动态（用两边都没有的值）；"WSL 独有"是推断 | 高（触发要有 WSL 插件加权限预设） |
| 3 | `web.searchProvider`（网页搜索服务） | WSL 里的 DS Bot 用补丁把这个设置的**默认值**改成了 `auto`（用户没设过这个值）。<br>设置页显示 Windows 的默认值 `deepseek-search-api`，**WSL 任务实际用的是 `auto`**；页面的服务列表里也没有 `auto`。<br>用户在页面上选了别的服务，会同步到 WSL，覆盖掉 DS Bot 的设置。<br>如果 Windows 端的值变成 `auto`，Windows 任务一搜索就会失败（DS Bot 说明：`WEB_PROVIDER_CONFIGURED_MISSING`），这一点没有实际触发 | 读取对比 + 动态写入 | 中 |
| 4 | `agent-default-model`、`subagent-model-selection-settings.allowedModels`（默认模型、子智能体可用模型） | 建任务时**不检查**模型是否存在，用两边都没有的模型或服务商，两边都能建成。出错推迟到发消息时（没有实际发消息）。模型目录（`session/modelCatalog`、`llm/listProviders`）只读 Windows：WSL 插件加的模型服务商在页面上选不到 | 动态（建任务）；发消息时的表现未测 | 中（推断） |
| 5 | 本机才有意义的值：`mcp-manager.servers` 的 `command`/`args`/`cwd`/`env`，以及各处的 `apiKeyEnv`（`llm-pi-ai` 的服务商、`web-search-deepseek`、`web-deepseek-api`） | 我们的同步（`settings.mjs` 的 `syncOps`）把两边都有的命名空间的用户层**原样复制**到 WSL，只排除了两个沙箱命名空间。<br>Windows 上配的 MCP 服务器（比如 `C:\...\node.exe` 或 `npx.cmd`）会在 WSL 里按同样的命令启动。<br>环境变量名在 WSL 里不一定存在。<br>反过来，**只想给 WSL 配的 MCP 服务器配不了**：页面的写入先到 Windows，再复制过去 | 静态（读代码） | 高（只要配了 MCP 就会遇到） |

### 第 2 类：合并列表里的单边标记

| # | 接口 | 现象 | 严重 |
|---|---|---|---|
| 6 | `agentPresets/list` | WSL 独有的预设一律标 `isDefault: false`，放在列表最后，名字加「 · WSL」。它的 `order` 保留 WSL 端的值（`tuned` 是 2，和 `ptc` 一样），但实际排在最后。<br>"默认"只有一个全局值，却由各自的 Host 解析，所以默认是 WSL 独有预设时，页面上没有任何一张卡标默认（同第 1 条） | 中 |
| 7 | `settings/describe` | 两边都有的命名空间，页面只显示 Windows 的值。WSL 端的默认值被插件改过时（第 3 条），设置页显示的不是 WSL 任务实际用的值 | 中 |

`session/list`、`session/search`、侧栏工作区、`dynamicCordisRunner/inventory` 的合并结果符合预期：两边的条目都在，WSL 的 id 加了前缀。

### 第 3 类：没合并的列表（页面只看到 Windows 的）

| # | 接口 | 现象 | 验证 | 严重 |
|---|---|---|---|---|
| 8 | `schedule/list`、`catalog`、`view`、`history` | 给 WSL 任务建的定时任务（页面建的，或模型在 WSL 任务里用工具建的）**在定时任务页上看不到**：页面列表为空，WSL 端有一条 | 动态 | 高（和第 13 条一起） |
| 9 | `web/listProviders` | WSL 端多一个搜索服务 `auto`（DS Bot），页面上没有 | 读取对比 | 中（和第 3 条一起） |
| 10 | `pluginInventory/list` | 设置里的「插件清单」和每个预设由哪些插件组成，只显示 Windows 的。WSL 端多出 18 个插件条目和 `tuned` 预设的组成，页面上都看不到。插件页本身有我们的 WSL 标签页，不受影响 | 读取对比 | 低 |
| 11 | `mcpManager/watch`、`probe`、`restart` | MCP 服务器状态只显示 Windows 的；WSL 端的 MCP 启动失败，页面上看不到；点"重启"只重启 Windows 端的 | 静态（流式接口；测试环境没有配 MCP） | 中 |
| 12 | `sessionReferenceResolver/candidates`（输入框里 @ 引用任务） | 候选只有同一边的任务：Windows 任务里 @ 不到 WSL 任务，反过来也一样。另外，WSL 任务候选里显示的是 WSL 路径（`/home/...`），没有像侧栏那样换成 Windows 能打开的写法 | 读取对比 | 低 |
| — | `permissionPresets/catalog`、`session/modelCatalog`、`llm/listProviders` | 测试环境里两边一样；只看 Windows 的后果见第 2、4 条 | 静态 | — |

**设计上本来就只看 Windows，不算问题的**：`account/*`、`speech/*`、`cuaAccess/*`、`remoteAccess/*`、`productAnalytics/*`、`directoryPicker/*`（WSL 有自己的目录选择路由），以及 `pluginManager/*`（插件页有 WSL 标签页）。

`officeKit/generation` 两边不同，它只是 Windows 端的缓存代号，影响很小。

### 第 4 类：按 id 写入

| # | 接口 | 现象 | 验证 | 严重 |
|---|---|---|---|---|
| 13 | `schedule/view`、`edit`、`run`、`history` | 这些调用只带定时任务 id（`schedule-…`），没有会话 id，所以总是送到 Windows。<br>对 WSL 任务的定时任务，页面上"查看""删除"返回的是 `ok: true`，值里写着 `code: schedule_not_found`，**看起来成功了，实际什么也没做**，WSL 端的定时任务还在 | 动态 | 高 |
| 14 | `schedule/create`，目标是"新建任务"（`target.kind` 为 `new` / `new_once`，或不填） | 调用里没有会话 id，总是在 Windows 端建，不管新任务页选的运行位置 | 静态 | 中 |

其余按 id 写入的接口都带会话 id，按 id 分流没有问题。`agentPresets/select` 和 `session/create` 已经有"WSL 独有预设不能用于 Windows 任务"的检查。

## 共同的根子

1. **一个全局值，两边各自解析**：第 1–5 条。DSH 的设计默认只有一个 Host，"默认"、"选中"、"服务商"都是一个值。我们把它同步到两边，可两边的可选范围不一样。
2. **主机级的列表和按 id 的操作没有来源**：第 8–14 条。条目只存在其中一边，可调用里没有任何东西指明是哪一边。我们处理插件运行（`dynamicCordisRunner`）时，靠"记住这个 id 是从哪边来的"解决了同样的问题，定时任务和 MCP 也可以照这个办法。

## 需要和所有者一起定的规则

每类都给了推荐方案，最终怎么定由所有者决定。

- **A. 指向清单的设置**：默认预设、默认权限预设、搜索服务、默认模型。
  - 方案一：**按运行位置各存一份**。页面上分别设"在 Windows 运行时"和"在 WSL 运行时"的默认。
  - 方案二：**一个值，哪边没有就用那边自己的默认**。我们在建任务时显式传那一边的默认值，页面标出"仅 WSL 生效，Windows 用 ×××"。
  - 方案三：一边独有的值不允许设成默认。最简单，但不算兼容。
  - 推荐方案二：只有一个"新任务默认"，含义最接近官方，也不会出现建不出任务的情况。
- **B. 本机才有意义的设置**：MCP 服务器、`apiKeyEnv`。
  - 推荐：不同步，两边各配各的。MCP 设置页按运行位置分开显示和写入。
  - 需要所有者确认：已经同步过去的 MCP 配置要不要清理。
- **C. 主机级列表**：定时任务、MCP 状态、搜索服务、权限预设、模型目录、插件清单。
  - 推荐：合并两边，每条标出来源（和预设的「 · WSL」一样）。
  - 按 id 的操作（定时任务的查看、编辑、运行、删除，MCP 重启）按"这个 id 来自哪边"分流。
  - 目标是"新建任务"的定时任务，跟随新任务页选的运行位置。
- **D. @ 引用任务**：是否允许跨边引用（需要两边能互相读对方任务的记录），还是只在候选里标明不能跨边。

## 复现

```bash
dev/scan/run.sh                 # 全部（会启动并在结束时停止测试 Desktop）
dev/scan/run.sh read            # 只读，不写设置
node dev/scan/summary.mjs ~/dshwsl-desk/scan   # 只看汇总
```

单条复现：第 1 条见 `docs/cross-host-scan.md`。第 8 和 13 条：对页面调 `schedule/create`（target 是一个 `wsl:` 会话），再调 `schedule/list` 和 `schedule/edit {action:'delete'}`，然后用 `HOME=$FAKE_HOME node dev/bridge-call.mjs '[["schedule/list",{"request":{}}]]'` 看 WSL 端，最后在 WSL 端删掉。
