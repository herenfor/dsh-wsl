# 跨两边的兼容规则（草案，待所有者定）

扫描报告见 [dev/scan/report-2026-11-12.md](../dev/scan/report-2026-11-12.md)。这里按报告最后一节的 A–D 逐条解释：问题是什么、成熟项目怎么做、我们能学什么、推荐方案。编号 #1–#14 对应报告里的发现。

参照的两个成熟项目，和我们的形状最像：

- **VS Code Remote - WSL**：Windows 上的界面，代码和扩展在 WSL 里运行。
- **Claude Code Desktop**：一个桌面界面，会话可以在本机、SSH 远程机器或云端运行，定时任务可以放在本机或云端。

## 先说从它们身上学到的五条原则

1. **每个设置都有"归属的机器"。**
   - VS Code 给每个设置标作用域（scope）。`machine` 和 `machine-overridable` 是"本机专属"：不参与设置同步，远程窗口也不继承本地的值，远程端要单独设。
   - Claude Code Desktop 连 SSH 时，会话读的是**远程机器自己**的 `~/.claude`（设置、技能、MCP）。只有界面和安全相关的几个键由 Desktop 在本机读。
   - 我们现在没有这一层，凡是两边都有的命名空间都整体复制。
2. **共享值 + 远端覆盖。** VS Code 在 WSL 窗口里沿用本地的用户设置，但有一个 "Remote [WSL]" 标签页，写在里面的值只在 WSL 里生效，并覆盖本地值。
3. **合并列表要标来源。**
   - VS Code 的扩展视图分成 "Local - Installed" 和 "WSL - Installed" 两组。
   - Claude Code Desktop 的定时任务页同时列出本机任务和云端任务，每条注明在哪里运行。
   - Claude Code Desktop 会话的详情面板会显示这个会话跑在哪台机器上。
4. **对象建的时候选好运行位置，之后的操作都回到它所在的地方。** Claude Code 建定时任务时要先选"本机"还是"云端"。本机任务存在本机的 `~/.claude/scheduled-tasks/`，云端任务存在云端，之后的编辑、运行、删除都对着它所在的那一边。
5. **坏值只影响它自己，不连累整体。**
   - Claude Code 的设置文件里个别条目无效时，只跳过那一条（Settings Warning），其余照常生效。
   - 模型选择器里某个模型用不了，就只去掉那一行。
   - 引用不存在的东西时，应该降级并告诉用户，而不是让整个操作失败。

## A. 指向清单的设置

覆盖报告 #1 默认预设、#2 默认权限预设、#3 搜索服务、#4 默认模型，以及 #6、#7。

### 问题

这些设置存的是一个名字（预设 id、权限预设名、搜索服务 id、模型 id）。DSH 只有一个 Host 时，这个名字一定能在本机清单里找到。现在有两个 Host，各自有一份清单：WSL 里装的插件会让 WSL 的清单多出几项。我们又把 Windows 的值原样同步到 WSL，于是会出现下面几种情况：

- 值只在 WSL 的清单里：Windows 任务建不出来（#1；#2 的机制相同）。
- 值在两边都能用，但 WSL 的默认值被插件改过：页面显示的是 Windows 的值，WSL 任务实际用的是另一个（#3）。
- 清单只读 Windows 的：WSL 独有的那几项在页面上选不到（#2、#3、#4）。
- 预设页没有任何一张卡标「新任务默认」（#6）。

### 成熟项目怎么做

- **VS Code**：设置默认对两边都生效，WSL 可以在 Remote 标签页单独覆盖。不存在"一个值在某一边无效就整体失败"：扩展找不到某个值时，用自己的默认值。
- **Claude Code**：
  - 默认模型（`model`）、默认权限模式（`permissions.defaultMode`）是**每台机器各自的** `~/.claude/settings.json`；SSH 会话读远程机器上的那份。
  - Desktop 的定时任务在创建时就把权限模式和模型存进任务本身；不选时用当时的设置和默认模型。
  - 个别值无效时跳过那一项，其余照常。

### 能学的

1. 解析要按 Host 进行：同一个值，在没有它的那一边要有一个合理的结果（用那一边自己的默认），并且明确告诉用户。
2. 允许"WSL 单独覆盖"，但不强制用户维护两份。
3. 清单要合并，并标出来源，用户才选得到 WSL 的东西。

### 方案

- **方案一：按运行位置各存一份**（VS Code 的 Remote 标签页）。
  - 做法：预设页、权限、搜索服务、模型的设置处，各有"Windows / WSL"两个值。
  - 优点：清楚，不会出错。
  - 缺点：界面要改的地方多，用户要理解两份。
- **方案二：一个值，哪边没有就用那一边的默认，页面标明**（Claude Code 的"坏值逐条降级"）。
  - 做法：
    - 建任务时，我们的路由检查这个值在目标 Host 上是否存在，不存在就显式传那一边的默认值，任务能建成。
    - 预设页给这张卡标「新任务默认（仅 WSL 任务）」，并说明 Windows 任务用的是哪一个。
  - 优点：改动小，界面基本不变，最接近官方"只有一个默认"的含义。
  - 缺点：Windows 任务"悄悄"用了别的预设，只能靠页面上的说明让用户知道。
- **方案三：一边独有的值不能设成默认**。最简单，但用户想默认用 WSL 的调优预设就做不到，不算兼容。

**推荐：先做方案二，以后需要时再加方案一的"WSL 单独覆盖"。** 两者可以叠加，正是 VS Code 的做法：默认共享，需要时远端覆盖。

具体到每个设置：

- **新任务默认预设（#1）**：
  - 建任务时降级到那一边的默认，并标出来。
  - 预设页合并后的列表里，默认卡始终有标记。
  - 用户在 Windows 文件夹建任务、又选了 WSL 独有预设时，现在的提示（"请把运行位置切到 WSL"）保留。
- **默认权限预设（#2）**：同上。另外，权限预设清单（`permissionPresets/catalog`）要合并两边、标出来源。
- **搜索服务（#3）**：
  - 服务列表合并两边，`auto` 标「WSL」。
  - 设置页显示"WSL 任务实际用：auto（由 DS Bot 设置）"。
  - 用户在页面上明确选了一个值，就两边都用这个值；某一边没有这个服务，就降级到那一边的默认。
- **默认模型（#4）**：
  - 模型目录合并两边、标出来源。
  - 某一边没有这个模型时，建任务就降级到那一边的默认模型，不留到发消息时才报错。

## B. 本机才有意义的设置

覆盖报告 #5：MCP 服务器、各种 `apiKeyEnv`。

### 问题

- **MCP 服务器**：配置里写的是一条要执行的命令（`command`、`args`、`cwd`、`env`）。
  - 在 Windows 上配的命令（比如 `npx.cmd`、`C:\...\node.exe`）被我们同步到 WSL 后，WSL 会照原样去启动，结果启动失败，页面上还看不到（见 C 类的 MCP 状态）。
  - 反过来，只想在 WSL 里跑的 MCP 服务器配不了：页面写入先落到 Windows，再被复制过去，也就是会同时在 Windows 上启动。
- **`apiKeyEnv`**：存的是环境变量名。Windows 上设了这个变量，WSL 里不一定有。

### 成熟项目怎么做

- **VS Code**：这类设置标为 `machine` 作用域：不同步，远程窗口不继承本地的值，要在远程端单独设。
- **Claude Code Desktop 的 SSH 会话**：
  - 官方文档写明：要在远程机器上的 `~/.claude.json` 或 `.mcp.json` 里配 MCP，"Claude Code 在那台机器上启动这些 stdio 服务器，所以要在远程机器上安装它们运行的命令"。
  - Desktop 不会把本机的 MCP 配置复制过去。
- **Claude Code 的 `.mcp.json`**：支持 `${VAR}` 和 `${VAR:-默认值}`，同一份配置可以在不同机器上展开成不同的值。

### 能学的

本机才有意义的设置不同步，在哪一边运行就在哪一边配。界面上要能看到、能编辑两边各自的那一份。

### 方案

- **推荐：**
  - 把 `mcp-manager` 和所有 `*ApiKeyEnv` 字段列为"本机专属"，不再同步，和现在的两个沙箱命名空间一样处理。
  - MCP 的设置页分 Windows 和 WSL 两组显示和写入。写 WSL 那一组时，请求送到 WSL 端，我们现在对 WSL 独有命名空间的写入已经是这样分流的。
- **已经同步过去的 WSL 配置**：推荐**保留，不删**。删掉可能让用户正在 WSL 里用的 MCP 消失；保留下来，以后就只是 WSL 自己的配置，用户可以在 WSL 那一组里自己删。这一点需要所有者确认。

## C. 主机级列表和按 id 的操作

覆盖报告 #8–#11、#13、#14：定时任务、MCP 状态、插件清单、搜索服务和模型目录。

### 问题

这些接口的调用里没有会话 id，我们的路由不知道该送哪边，就一律送 Windows：

- **定时任务（#8、#13、#14）**：
  - WSL 任务里建的定时任务存在 WSL 端，页面的定时任务列表里看不到。
  - 在页面上查看、编辑、删除这类定时任务，请求都去了 Windows，返回"找不到"，却显示成功。
  - "新建任务"类的定时任务不管运行位置怎么选，都建在 Windows。
- **MCP 状态（#11）**：只显示 Windows 的；"重启"只重启 Windows 端的。
- **插件清单（#10）、搜索服务（#9）、权限预设和模型目录**：只显示 Windows 的。

### 成熟项目怎么做

- **Claude Code Desktop 的定时任务**：
  - 一个页面同时列出本机任务和云端任务，各自注明在哪里运行。
  - 新建时先选"本机"还是"云端"，任务存在它运行的地方；后续的编辑、立即运行、删除都针对那一边。
- **VS Code**：扩展视图分 "Local - Installed" 和 "WSL - Installed" 两组，安装、卸载时明确是装在哪一边。
- **我们自己已有的做法**：
  - 会话和工作区的 id 加 `wsl:` 前缀，所以任何带这个 id 的调用都能送对地方。
  - 插件运行（`dynamicCordisRunner`）记住"这个运行 id 来自 WSL"，后续调用照此分流。

### 能学的

主机级的东西也要带来源：列表合并时，每一条都知道自己属于哪一边，对它的操作就送回那一边。

### 方案（推荐）

- **定时任务**：
  - 列表合并两边，WSL 的条目标「WSL」。
  - 定时任务 id 和会话 id 一样加 `wsl:` 前缀，查看、编辑、运行、删除就能按 id 自动送对地方，"显示成功其实什么也没做"的问题也随之消失。
  - "新建任务"类的定时任务按新任务页选的运行位置建；定时任务对话框里最好也能选位置，和 Claude Code 的"本机 / 云端"一样。
- **MCP 状态**：合并两边，按位置分组。重启、探测按条目的来源送到那一边。这一条和 B 一起做。
- **插件清单、搜索服务、权限预设、模型目录**：合并两边，标出来源。从中选值的规则按 A 处理。
- **不合并的**：账户、语音、屏幕操作、目录选择、插件管理（已有 WSL 标签页）。这些本来就属于 Windows 这台机器。

## D. @ 引用任务

覆盖报告 #12。

### 问题

在输入框里 @ 一个任务，模型就能读到那个任务的记录。这个读取由当前任务所在的 Host 完成，它只认识自己的任务，所以 Windows 任务里 @ 不到 WSL 任务，反过来也一样。另外，WSL 任务的候选里显示的是 WSL 路径，没有换成 Windows 能打开的写法。

### 成熟项目怎么做

- **VS Code**：一个窗口只连一个 Host，不能在本地窗口里引用远程的文件。
- **Claude Code**：会话记录存在运行它的那台机器上，恢复会话（`--resume`）也只在同一台机器、同一个项目里可用。SSH 会话的记录在远程机器上。

两者都不做跨机器引用。

### 方案

- **推荐，先做**：候选只列同一边的任务（保持现在的行为），在候选列表底部说明"WSL 中的任务只能在 WSL 任务里引用"；顺手把 WSL 任务的路径换成 Windows 写法。
- **以后再说**：真正跨边引用需要我们的插件把另一边任务的记录取过来、转成一段文字交给当前任务。工作量不小，也要先确认官方的引用格式能不能这样喂。
